# Кратковременный конфликт владельца sing-box при reload

## Инцидент

На 192.168.90.1, Forkop 2.1.1 / Sing-Box X 1.0.3, отключение секции
adblock 9 октября 2026 в 16:12 по журналу роутера сохранилось в UCI.
Обновление списков завершилось, но финальный reload list-content был отвергнут
с сообщением `sing-box process ownership is ambiguous`.
Маркер `/var/run/forkop/list-update.reload` содержал `apply-failed`, а старый
конфиг sing-box всё ещё содержал adblock. Работающий процесс сохранялся.

Последующие read-only проверки обнаружили единственный PID 11973, совпадающий
с procd, и успешное доказательство владения. Второй процесс непосредственно в
момент инцидента не записан в журнал: конкретную кратковременную команду
ретроспективно установить нельзя. Пока шла диагностика, конфигурация роутера
была изменена извне: PID стал 6795, маркер исчез, adblock отсутствовал в UCI и
в списке rule_set текущего конфига. Эта работа не меняла роутер.

## Дефект и исправление

`sing_box_process_count()` учитывает все процессы с exe basename `sing-box`,
в том числе version, check и rule-set. `sing_box_process_conflict()` раньше
принимал решение по одному наблюдению. Пересечение с кратковременной командой
могло навсегда оставить уже сохранённое изменение неприменённым.

Теперь при конфликте выполняются до трёх повторных проверок с интервалом
одна секунда. Каждый раз используется прежнее строгое доказательство:
единственный процесс, PID procd, исполняемый файл и start ticks до/после скана.
Постоянный второй процесс или неверный PID procd по-прежнему приводят к отказу
start/reload/restart и внутренней остановки. Явный пользовательский Stop
сохраняет прежний контракт: убирает перехват и завершает все sing-box процессы.
Проверка никого не убивает и не исключает процессы по аргументам командной строки.
Если неоднозначность сохраняется более трёх секунд, отказ в защищённых
переходах и сохранение старой политики остаются ожидаемым безопасным результатом.

Полный пакетный тест также обнаружил несогласованный ответ LuCI:
`forkop.running=0`, `restart_blocked=0`, `sing_box.running=1` после завершения
кратковременного процесса. `current_ui_state_json()` вычислял здоровье до
ожидания проверки владельца. Теперь здоровье вычисляется после этой проверки;
добавлено обязательное утверждение `forkop.running=1` в тест кратковременного
процесса. Это второе небольшое изменение backend; JS интерфейса не меняется
за исключением встроенного номера версии при сборке.

## Проверка

Использована существующая OpenWrt 25 VM 192.168.1.1: Forkop 2.1.0,
Sing-Box X 1.0.2. До изменений сохранены apk info -v и ubus service list
в `/tmp/forkop-ownership-fix/`. Тесты запускали только свои процессы и меняли
только эту VM; исходный UCI и state.uc сохранены и восстановлены.

- Новый `tests/singbox_transient_process.sh`: старый установленный код
  воспроизводимо отказал при двухсекундном вспомогательном процессе;
  исправленный код дождался завершения. Постоянный второй процесс отвергнут.
  Для детерминированного пересечения используется копия BusyBox с exe basename
  sing-box; сетевые слушатели вспомогательным процессом не создаются.
- `tests/singbox_single_process.sh`: проверяет настоящий второй sing-box,
  удалённый executable, неверный procd PID, сохранение рабочего PID и nft policy.
- `tests/list_update_final_reload.sh`: прошли синхронный apply, очередь,
  сохранение маркера при ошибке и выбор локального повторного применения.
- Реальный установленный исправленный state.uc: reload при кратковременном
  втором процессе вернул 0. Добавлена отдельная локальная block-секция с
  доменом ads.ownership-test.invalid при сохранённой исходной direct-секции.
  Её включение и отключение через UCI/reload вернули 0, единственный процесс
  принадлежал procd. Последующая усиленная проверка обнаружила ошибку этой
  ранней фикстуры: использовалось неподдерживаемое поле `domains` вместо
  `domain_suffix`. Отсутствие домена после отключения не доказывало его удаление.
  Эта ранняя проверка содержимого исключена из доказательств готовности;
  повторный пакетный тест требует наличия домена до отключения и отсутствия после.
- Попытка отключить единственную исходную секцию отдельно дала ожидаемую
  ошибку `no enabled sections`; она не используется как доказательство
  исправления. Исходная конфигурация восстановлена.
- В конце cmp подтвердил восстановление UCI, исходного state.uc и неизменный
  набор пакетов; проверка единственного процесса службы успешна.

## Релиз

Исправления относятся к Forkop backend: проверка владельца и согласованный
статус LuCI. Пересборка sing-box X не требуется.

## Окончательная пакетная проверка 2.1.2

Все шесть APK/IPK собраны штатным build.sh из тега 2.1.1 (совпадает с текущим
main HEAD 9dd0f986) с двумя изменёнными backend-файлами state.uc и ui.uc.
Посторонние незакоммиченные изменения зеркала и документации в сборку не вошли.
Проверка всех извлечённых payload-файлов относительно опубликованных 2.1.1
подтвердила только эти два изменения и поля версии constants.uc/main.js;
содержимое пакетов переводов совпадает.

Окончательные пакеты находятся в `tmp/ownership212-validation/packages`.
Их длины и SHA-256 зафиксированы в `tmp/ownership212-validation/manifest.json`;
SHA-256 всех шести файлов на обеих VM совпали с локальным манифестом.
Пакеты отката 2.1.0 проверены по публичному release.json зеркала, 2.1.1 —
по сохранённым хешам опубликованного комплекта.

Существующие VMware VM OpenWrt 25.12.5 (APK) и 24.10.8 (IPK), обе с
Sing-Box X 1.0.2, прошли полный финальный прогон:

- реальная установка 2.1.1, обновление до окончательной 2.1.2 при имеющемся
  pending reload и повторная установка тех же пакетов;
- побайтовое сохранение UCI Forkop при обновлении и повторной установке;
- неизменный SHA-256 исполняемого файла sing-box, единственный процесс procd,
  проверка сгенерированного конфига и ответы локального DNS;
- кратковременный второй executable не вызывает постоянный отказ, статус
  LuCI после ожидания имеет running=1 и restart_blocked=0;
- настоящий постоянный второй sing-box, удалённый executable и неверный
  procd PID блокируют защищённые переходы;
- start и внутренние stop (CLI/init.d) при конфликте не изменяют DNS,
  nft policy и PID работающего процесса; LuCI блокирует restart и сохраняет
  доступность явного Stop;
- асинхронные stop/start/restart через тот же backend и polling статуса,
  которые вызывают кнопки LuCI;
- LuCI restart одновременно с config/list-content reload: запросы обработаны,
  pending marker потреблён, reload lock освобождён, служба и DNS работают;
- локальное block-правило с правильным полем domain_suffix присутствует до
  отключения и отсутствует после reload при двухсекундном вспомогательном
  процессе; UI-ответ при таком процессе занял две секунды на обеих VM;
- явный Stop при дополнительном процессе завершает все sing-box процессы
  и удаляет nft interception; CLI start/restart восстанавливают работу;
- реальный откат пакетов к 2.1.1 с сохранением настроек и работоспособности.

Оба финальных протокола содержат ALL_RELEASE_CHECKS_PASSED,
BASELINE_RESTORED и завершены с кодом 0. Исходные пакеты 2.1.0 восстановлены;
Forkop, DHCP и sing-box UCI совпадают с сохранёнными файлами. После восстановления
проверено совпадение набора работающих procd instances и их команд (PID могут
меняться). UI показывает running=1, restart_blocked=0, dns_configured=1.

Протоколы сохранены в `tmp/ownership212-validation/vm25-evidence` и
`tmp/ownership212-validation/vm24-evidence`, включая прежние неуспешные прогоны.
Они выявили ошибки тестовых ожиданий (ранний restart во время занятого lock,
поле domains вместо domain_suffix, явный Stop вместо защищённого internal Stop),
а также реальный несогласованный статус LuCI, исправленный в окончательном
комплекте. Ошибочные ранние утверждения не используются для оценки готовности.

В WSL прошли семь выбранных регрессионных наборов: list_update_final_reload,
latency_reload_serialization, dns_reload_config, build_version,
native_process_identity, list_update_reload_policy, opkg_lock_retry.
Протокол — `tmp/ownership212-validation/regression.log`.

Итог: этот точный комплект 2.1.2 готов к выпуску в пределах проверенного
исправления. Проверки не включали установку на рабочий ARM-роутер, реальную
пользовательскую подписку или дополнительную проверку транспортов sing-box.
Релиз/тег не публиковались, зеркало не синхронизировалось,
192.168.90.1 не обновлялся и не перезапускался этой работой.

## Установка на рабочий роутер после разрешения пользователя

9 октября пользователь отдельно разрешил установить исправление на 192.168.90.1
(GL-MT6000, OpenWrt APK). Установлены три точных проверенных APK 2.1.2:
forkop, luci-app-forkop и luci-i18n-forkop-ru. До изменения сохранены package/service
inventories, Forkop/DHCP/sing-box UCI, прежний сгенерированный конфиг и SHA-256
исполняемого файла. Все шесть APK кандидата и отката проверены на роутере
по SHA-256; APK Forkop имеет architecture noarch.

Закрытая резервная копия и три APK 2.1.1 для отката сохранены на роутере в
`/root/forkop-backups/2026-10-09-2.1.2` (режим каталога 0700). Приватные
SSH-ключи не копировались. Конфигурации с секретами остались на роутере.

Финальная проверка завершилась INSTALL_AND_VERIFY_PASSED:

- все три пакета показывают 2.1.2;
- Sing-Box X остался 1.0.3-r1, SHA-256 executable совпадает с исходным;
- SHA-256 установленных state.uc/ui.uc совпадают с проверенными исходниками;
- Forkop и sing-box UCI побайтово сохранились;
- единственный процесс sing-box принадлежит procd, конфиг проходит check;
- локальный DNS отвечает, UI возвращает running=1, restart_blocked=0,
  dns_configured=1, pending/reload lock завершены;
- штатный фоновый тест задержек для 38 независимых outbounds завершился
  успешно (это не утверждение о доступности каждого узла или совместимости
  всех транспортов).

Локальные несекретные протоколы: `tmp/router90-212-install/runner.log`,
`install.log`, `ui.after.json`, `config-check.log`. Резервная копия не удалялась;
временный staging установки очищен. GitHub-релиз и зеркало не публиковались
и не менялись этой установкой.
