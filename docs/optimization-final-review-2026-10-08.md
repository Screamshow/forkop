# Итоговое ревью двух чатов — Forkop X 2.1.0-canary.1

> Следующий этап завершён: точные пакеты 2.1.0-canary.1, SDK, clean install/upgrade/rollback/reboot, DNS/UI и парная router-серия. Актуальные результаты: [canary-2.1.0-validation-2026-10-08.md](canary-2.1.0-validation-2026-10-08.md). Публикации нет; клиентский пилот ждёт устройств.

Дата: 8 октября 2026. Сверены предыдущий чат «Оценить UPX и Rust для sing-box» (01a11837-8132-7ce0-9dd8-681b54036197), включая начальный аудит и передачу состояния, текущий чат, git diff и локальные отчёты. Этот документ фиксирует актуальный итог; старые отчёты описывают свои этапы.

## Статус

Работа на существующей main, незакоммиченные изменения сохранены. Релиз не создан и не опубликован. Последний проверенный и установленный на пользовательском роутере комплект — текстовый backend/LuCI с тестовой версией 2.0.0 из tmp/optimization-review-20261008/plan-stage2/packages. Sing-Box X остался 1.0.1-r1, executable 1.14.2-x-1.0.1. Ядро в этом этапе не обновлялось. Минимальный возраст core перед успехом — 8 секунд.

Последняя успешная установка и проверки роутера описаны в optimization-plan-stage2-2026-10-08.md; откат и снимки — /root/forkop-plan-stage2c-20261008. В этом итоговом ревью новых воздействий на роутеры не выполнялось. Обе ВМ после bytecode-эксперимента возвращены на текстовый backend и проверены; подробности в bytecode-space-check-2026-10-08.md.

## Что реализовано и входит в описание релиза

1. Нет пустых ожиданий остановки отсутствующих провайдеров. Остановка принадлежащих Forkop процессов, TERM/grace/KILL сохранены. Отдельный zapret-manager не включён в lifecycle Forkop; последняя проверка сохранила nfqws PID 2809/2810.
2. Native fs.readlink вместо множества внешних readlink в проверках процессов. Владение процессом, start_ticks, чужой core и deleted executable по-прежнему проверяются.
3. Проверка версии ждёт завершения native system с deadline вместо секундного polling. Ошибочный, неполный ответ и timeout не принимаются.
4. Неизменившиеся SRS повторно используют результат успешной валидации после проверки SHA-256. Legacy proof перепроверяется один раз; новые, изменённые и повреждённые файлы идут через parser. Atomic publication, last-good и persistent/runtime fallback сохранены.
5. Убраны повторные определения версии при генерации конфигурации и подготовке подписок. Snapshot ограничен операцией, custom User-Agent сохранён, неуспешное определение не кэшируется.
6. DNS reload внедрён для поддерживаемых штатных конфигураций. Проверяются применённый config, нужный procd instance, процесс, его DNS-сокеты и protocol response; ожидание ограничено, при отказе выполняется restart. Учтены multiple instances, custom port, port=0, disabled и dont_touch_dhcp. DNS-транзакции и восстановление между stop/start сохранены.
7. Удалены семь подтверждённых неиспользуемых функций, затем пустая nft snapshot-заглушка и остатки её фиктивного состояния. Реальная candidate/committed-generation схема и deferred retry сохранены. Миграции и совместимость старых вариантов ядра не удалены.
8. Убрана обязательная зависимость coreutils-base64 из пакетов, validator и установщика. Встроенное base64 ucode использовалось до этого этапа; новый декодер не создавался. Уже установленный пакет автоматически не удаляется.
9. Компактная упаковка main.js и восьми ручных JS LuCI. Ручные исходники читаемы; AST equivalence проверяет упаковку, manifest выявляет устаревший generated overlay. Имена и LuCI directives сохранены.
10. DHCP detection установщика перенесён в его ucode helper. При отсутствии доказательства выполняется обычная остановка. Актуализированы архитектурные и installer-тесты; это не новая смена default ядра на X.

Колебание 38,68/39,40 не доказывает регрессию; подписки, списки и check имеют переменную длительность. Пользовательская отметка 47 с округлена и не является парным исходным benchmark. Последний этап минификации новых замеров restart не добавил.

Не суммировать вложенные строки профиля. 21,66 с в прежнем DNS-эксперименте относится к неполному внутреннему пути; 6,3 с на ВМ включало экспериментальный возраст core 2 секунды. Ни одно не является результатом текущего полного router manual_restart.

Сама генерация JSON занимает около 0,43–0,44 с; прежние 3–4 с включали весь init-config и sing-box check. В новых профилях init-config не показал общего ускорения: check вырос с 0,82 до 2,07–3,10 с, причина не установлена. Нельзя заявлять «генератор ускорен с 3,6 до 0,43 с».

Полное ускорение boot, скорость трафика, снижение CPU/RAM не доказаны. Reboot наблюдения по uptime/SSH не подменяют момент готовности. Раннее утверждение «bytecode экономит 522 КиБ флеша» в предыдущем чате было слишком широким: тогда измерялся размер файлов, а не flash.

## Что проверено и где остаются ограничения

559 frontend-тестов, TypeScript/build и AST-проверка; backend/installer regression и DNS failure matrix. На обеих ВМ проверены реальные APK/IPK установка, откат и повторная установка, переход со старого canary, сохранение UCI/core, runtime и DNS. LuCI: шесть вкладок, переводы, секционный редактор, реальный Save & Apply и восстановление тестового изменения. На роутере подтверждены один core, DNS, HTTPS через SOCKS, сохранность UCI/core, UI без page errors и отсутствие profiling overlays.

Функциональный reboot оптимизаций запуска/SRS/DNS проверен на обеих ВМ через source overlay. Последний точный пакетный комплект с финальной минификацией и installer cleanup после reboot ещё не проверен. Чистая установка публичного 2.0.0 из предыдущего чата также не равна чистой установке будущих финальных 2.1.0 пакетов.

DNS ускорение имеет область поддержки: обычный OpenWrt dnsmasq с проверенными IPv4 listeners. IPv6-only и произвольные изменения сторонних include/confdir во время перехода не проверены. Для конфигураций вне области reload сохранён прежний restart-путь. Универсальную безопасность на всех клиентских роутерах заявлять нельзя; после закрытия финальных проверок уместен ограниченный canary с откатом.

## Что отложено или не дало основания для внедрения

- Bytecode: подготовлены opt-in сборка и совместимый pinned compiler; default остаётся текстовым. Кандидат 64 модулей прошёл install/restart и отдельные recovery-тесты. Реальная повторяемая экономия на ext4 обеих ВМ — 528 КиБ; APK/IPK при этом больше на 36,09/40,07 КиБ. Выигрыш RAM/скорости не измерен, на f2fs роутера физический выигрыш не подтверждён. Не включать в canary; затраты на полную compatibility/recovery/reboot матрицу сейчас не оправданы величиной выигрыша.
- Порог 8 секунд оставлен решением пользователя. При убийстве core на возрасте 3 с порог 2 с уже успевал объявить успех и оставлял DNS outage до respawn; 5/8 с выявляли отказ и восстанавливали DNS. Безопасность 5 с для иных отказов не доказана.
- Параллелизм списков/подписок не внедрён. Измеренная сеть обычных списков около 0,61 с, подписки 0,15–0,17 с; локальная обработка/импорт заметнее. Parallel parser давал нестабильный выигрыш.
- Sing-Box X уже UPX-сжат. Дополнительный CLI-кандидат экономил лишь 99512 байт ARM64 / 117580 байт x86_64, около 1%; не установлен и не входит в релиз. Перевод на Rust и удаление протоколов не выполнялись.
- bind-dig сохранён: он нужен DNS readiness/failover/диагностике. Удаление требует полноценной замены, а не исключения зависимости.
- Извлечение тестовых fixture-entrypoints из backend остаётся кандидатом, оценка около 40 КиБ текста не подтверждена готовой безопасной правкой. Список single-reference функций сам по себе не разрешает удалять код.
- Graceful shutdown/отсутствующий STOP в init.d и предупреждение unclean shutdown остаются отдельным расследованием. Скрывать предупреждение или менять порядок DNS при shutdown без тестов не следует.

## Что осталось перед выпуском

1. Зафиксировать текстовый scope релиза. Исключить opt-in bytecode wiring из release diff либо явно оставить его только как отдельный эксперимент; сейчас он выключен, но присутствует в рабочем build.sh/Makefile. Ничего из предыдущего этапа в ходе ревью не удалялось.
2. Подготовить точные финальные 2.1.0-canary.1 APK/IPK и manifest; проверить generated inputs в чистой сборке и полный поддерживаемый SDK/Makefile путь (до сих пор пакеты проверены через build.sh).
3. На обеих ВМ прогнать именно эти пакеты: clean install, обновление с поддерживаемой предыдущей версии, точный rollback, reboot и runtime/DNS/UI. Оставить рабочее окружение и удалить временные production-подмены.
4. Если нужен достоверный процент ускорения, выполнить парную серию одного и того же полного manual_restart с сохранённой конфигурацией и фиксированными данными; отдельно описать сеть и check. Без серии публиковать только текущие наблюдения.
5. После этого — ограниченный клиентский canary с подготовленным откатом. Публикация только по отдельному запросу пользователя.

Дополнительные оптимизации — fixture extraction, локальные imports/UCI/process launches по новому профилю и orderly shutdown. Их оценивать отдельно; ещё несколько секунд заранее не обещать. Крупные доказанные простые выигрыши уже реализованы.
