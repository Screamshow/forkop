# DNS reload и списки — исследование 8 октября 2026

Проверены существующие OpenWrt 24/25 ВМ и GL-MT6000 192.168.90.1. Production-модули dns/apply.uc и singbox/ruleset_cache.uc не изменялись. Эксперименты через временные скрипты и DNSMASQ_INIT, без установки пакетов. Постоянного внедрения нет.

## dnsmasq reload

На всех трёх системах reload_service() вызывает rc_procd start_service и procd_send_signal. start_service генерирует конфигурацию и передаёт её procd через procd_set_param file $CONFIGFILE. Поэтому reload при изменении конфигурации тоже может перезапустить dnsmasq; это не обещание отсутствия перезапуска. Команда возвращается до гарантированной готовности DNS.

На ВМ временно добавлялась запись forkop-reload-probe.invalid -> 192.0.2.123. После reload проверялась именно новая запись, затем исходный dhcp восстанавливался побайтно, проверялось исчезновение записи. EXIT trap дополнительно выполнял обычный dnsmasq restart. Forkop оставался работающим. Первый технический запуск остановился из-за неподдерживаемого sleep .05; trap восстановил конфигурацию. Повторы используют встроенный sleep(50) ucode.

| Проверка | OpenWrt 25 | OpenWrt 24 |
|---|---:|---:|
| Reload без изменения: DNS отвечает от начала команды, 3 повтора | 0,07 / 0,06 / 0,06 с | 0,06 / 0,07 / 0,06 с |
| Новая запись применена | 0,13 с | 0,12 с |
| После восстановления исходной конфигурации DNS отвечает | 0,12 с | 0,12 с |
| Полный forkop restart со штатным restart DNS | 19,95 с | 19,51 с |
| Полный forkop restart с экспериментальным reload + ожиданием DNS | 18,18 с | 19,21 с |

В одном DNS-переходе OpenWrt 24 dig попал в окно недоступности и израсходовал почти секунду на timeout. Поэтому это предварительный стендовый wrapper, а не готовый общий контракт DNS-готовности.

На реальном роутере перед воздействием сохранены пакеты, состояние procd, dhcp/forkop, код DNS и хэши в root-only /tmp/forkop-dns-readiness.gcBaGe и /tmp/forkop-dns-runtime.OAeMlH. Три reload без изменений: 0,27 с до возврата команды, 0,30 с до DNS-ответа каждый раз.

Один экспериментальный forkop restart занял 21,66 с. Его DNS-переходы restore/configure заняли 0,39 и 0,40 с. Предыдущий профиль обычного внутреннего restart — 27,22 с, включая DNS restore 2,60 с и configure 2,98 с. Сопоставление указывает на выигрыш около 5 секунд, но не является парным повторяемым измерением и не включает подготовку сетевых данных manual_restart.

После теста: Forkop и sing-box running, один процесс sing-box, DNS отвечает, HTTPS через SOCKS 192.168.90.1:2080 вернул 204, Clash API отвечает. Отдельный Zapret сохранил PID 2809/2810. Код DNS и UCI Forkop совпали с резервными копиями. В dhcp изменился только forkop_dns_transaction_id, что штатно для новой транзакции; после исключения этого поля файлы совпадают. Поэтому полный хэш dhcp после restart ожидаемо отличается. Первый HTTPS probe ошибочно обращался к 127.0.0.1:2080, где mixed inbound не слушает; повтор на фактическом адресе успешен.

Для production нужны bounded deadline, проверка готовности именно применённой конфигурации/управляемого DNS-instance, учёт port=0/custom port/multiple instances, fallback restart при ошибке или timeout и проверка отката. Просто localhost-ответ старого процесса или status=running недостаточен. PID procd jail-wrapper отличается от PID владельца DNS-сокета; прямое сравнение этих PID тоже неверно. dont_touch_dhcp и DNS transaction ownership должны сохранить нынешнюю семантику. Убирать восстановление DNS между stop/start не предлагаем: /etc/resolv.conf пользуется localhost, а перенаправление на остановленный sing-box создаёт неработающий DNS.

## Списки: где реально тратится время

В ruleset-cache роутера восемь записей, общий скачанный объём 1 553 632 байта. Использовались штатные candidate_urls, Bootstrap fallback, curl timeouts/лимит файла и valid_cache, прямой путь согласно download_lists_via_proxy=0. URL и конфигурации с секретами оставались на роутере. Активные файлы кэша и manifests не изменялись.

Статический анализ: prepare_list_downloads() дедуплицирует URL, затем последовательно скачивает и проверяет источники. refresh_manifest() также последовательно вызывает refresh_entry(), после чего пишет общий manifest. Скачивание и независимую обработку можно распараллелить, но shared state, публикация поколения и nft-транзакция требуют единого координатора.

Диагностический benchmark скачивает и проверяет файлы в частный /tmp-каталог. Параллельные задачи запускаются ограниченными группами; это не готовая production-очередь и не чистый benchmark сетевой загрузки.

| Задач одновременно | Два точных замера скачивания + проверки |
|---|---:|
| 1 | 6,182 / 5,359 с |
| 2 | 4,276 / 3,854 с |
| 4 | 1,644 / 3,627 с |

Во всех запусках 0 ошибок; файлы совпали по SHA-256. Дополнительный раздельный замер: последовательный путь 5,582 с, сумма network около 0,78 с, validation около 4,50 с. В его параллельном повторе две задачи заняли 5,859 с: проверка крупнейшего SRS замедлилась, тогда как сеть оставалась быстрой. Результат зависит от CPU/разбора/планирования, а не только от сетевых ожиданий. Четыре конкурентных разбора SRS дополнительно требуют оценки пикового RAM на маленьких ВМ; измерения GL-MT6000 этого не гарантируют.

Главный кандидат — не запускать sing-box rule-set match повторно для неизменившегося уже проверенного бинарного SRS. Сейчас refresh_entry() сначала выполняет valid_cache(temporary), и только потом сравнивает MD5 с активным файлом. Каждый временный файл получает новый путь и поэтому не использует marker .validated старого кэша. Это снова запускает UPX-packed executable для каждого SRS.

Второй диагностический вариант читает marker доверенного старого файла, проверяет его stat signature, сравнивает SHA-256 скачанного файла и старого, повторно проверяет stat signature. При совпадении не запускает повторный разбор; иначе оставляет штатную проверку. Все операции записи остаются только во временном каталоге.

Три последовательных повтора: 1,174 / 1,192 / 1,153 с. Во всех восьми источниках marker действителен, SHA-256 совпал; 0 ошибок, все скачанные файлы одинаковы. Это доказывает потенциал примерно четырёх секунд на текущем наборе, но ещё не является внедрением или общим результатом для изменившихся списков.

Перед production нужны проверки изменившегося/битого SRS, отсутствующего/устаревшего marker, замены файла и гонки между хэшем/проверкой, runtime-only кэша, восстановления на flash и abort обновления. Быстрый путь допустим только от уже проверенного содержимого; при сомнении штатная валидация обязательна. Lock, atomic rename, последние рабочие файлы и persistent/runtime manifests сохраняются.

Порядок дальнейшей работы: (1) DNS reload с полноценной проверкой применения и откатом; (2) безопасный SHA-256 fast path неизменившихся SRS; (3) очередь максимум двух скачиваний, независимые временные файлы, общий бюджет памяти/места и последовательная публикация. Параллельные тяжёлые SRS-валидации пока не рекомендуем включать по умолчанию.
