# Forkop X 1.16.1: первый запуск со списками через выбранную секцию

Дата проверки: 4 октября 2026 (Europe/Moscow).

## Реализация

Отдельный временный download-transport удалён. Вызовы helper из updates.uc,
команды generate-list-download-config и отдельный тест helper удалены.
Загрузчик снова использует только штатный service proxy.

При отсутствии валидного поколения списков lifecycle под reload.lock сначала
подготавливает subscription caches. Если списки скачиваются через секцию,
он останавливает прежний управляемый PID с проверкой PID/starttime и владельца
procd, генерирует и проверяет предварительную конфигурацию штатным генератором
и запускает обычный procd-сервис sing-box. Эта конфигурация содержит подключения
и loopback mixed listener выбранной секции, без TPROXY, DNS listener и правил,
зависящих от ещё не скачанных списков. Отдельного процесса вне procd нет.

Обычный list-update выполняет транзакционную загрузку с PREPARE_ONLY под той же
блокировкой. После загрузки lifecycle подтверждает завершение предварительного
PID, восстанавливает прежний config.json и продолжает штатную генерацию полной
конфигурации, применение nft и запуск. Если прежнего config.json не было,
предварительный файл удаляется после остановки. Ошибка загрузки или проверки
полной конфигурации не объявляется успешным запуском. Рабочий валидный кэш
используется без обязательного повторного скачивания.

Проверки владельца procd, единственного процесса, PID/starttime, блокировки,
конфигурации и существующий rollback сохранены. sing-box check выполняется без
работающего managed runtime. Готовность watchdog выставляется после финальной
проверки полного runtime, включая restart и восстановление через reload;
stop/cleanup снимают готовность. Изменения каталога и архивов зеркала в scripts/
сохранены. Hardcoded Discord-подсети не добавлялись.

Дополнительная проверка конкурентных действий выявила реальную гонку:
`forkop reload` обходил init.d-блокировку, а UI worker терял аргумент
`manual-ui-restart` и выполнял обычный init.d restart во время обновления
подписки. Проверка владельца sing-box корректно отклоняла пересекающийся
запуск, но cleanup останавливал runtime. Этот результат не засчитывается
как успешная проверка, даже если последующий retry восстанавливал сервис.

CLI reload теперь проходит через штатную initd очередь и блокировку.
До постановки в очередь неоднозначный владелец sing-box отклоняется с ошибкой,
с сохранением прежних PID и nft policy. Initd после захвата блокировки вызывает
существующий lifecycle напрямую. UI worker передаёт четвёртый аргумент и
использует подготовленный manual restart, который при занятой блокировке
отказывает до остановки runtime. Владельцем startup lock стал живой initd
worker: при rcS-запуске shell-родитель может завершиться раньше него.

Регрессия `tests/lifecycle_concurrency_vm.sh` удерживает загрузку подписки,
одновременно запрашивает CLI reload и LuCI restart, проверяет сохранение
рабочего PID во время I/O и отказ занятого ручного restart. Затем проверяет
полную финальную конфигурацию, удаление узла, единственного владельца, DNS
и отсутствие fatal ошибки запуска в журнале именно этого прогона.
В конкурентном прогоне использован `on_config_change`: совпадающее внутреннее
изменение UCI может быть корректно пропущено существующим trigger guard.
Принудительная постановка `list-content` при живом владельце lock отдельно
проверена `list_update_final_reload` с окончательными исходниками на обеих ВМ;
проверены queue acknowledgement, pending marker и повторное локальное применение.

## Сравнение с upstream

Проверены актуальные исходники ushan0v/forkop/main:
[lifecycle.uc](https://github.com/ushan0v/forkop/blob/main/forkop/files/usr/lib/service/lifecycle.uc)
запускает основной sing-box перед фоновым list-update;
[generator.uc](https://github.com/ushan0v/forkop/blob/main/forkop/files/usr/lib/singbox/generator.uc)
задаёт download_detour для remote rulesets. В Forkop X сохранены более строгая
проверка локального поколения, управляемая смена PID и проверка полной политики
перед успешным завершением запуска.

OpenWrt 25.12.5/APK, sing-box tiny 1.13.21 и
OpenWrt 24.10.8/OPKG, sing-box tiny 1.12.22.
Перед изменениями заново сохранены пакеты, процессы, procd service state,
конфигурации и файлы. Начальное состояние обеих ВМ: Forkop 1.14.9, работает
один sing-box. Старые испытания отдельного процесса из discord-1.16.1-verify
сохранены как история и не являются подтверждением этой реализации.

Проверки list_cache, list_update_final_reload, community_subnet_routes,
list_cache_space и list_download_space прошли на обеих ВМ. ShellCheck итоговых
VM-тестов и три теста каталога релизов прошли. На OpenWrt 25 один прогон
list_download_space потребовал повторения после ошибки очистки tmpfs; проверки
самой загрузки прошли и в первом прогоне, повтор завершился полностью.

Дополнительные проверки выполнялись без новых резервных копий ВМ по просьбе
пользователя; для восстановления использованы уже сохранённые исходные файлы
и пакеты. Настоящие reboot проверены по смене kernel boot_id, полной стабильной
политике, watchdog.ready, сохранённому list-cache и непустому DNS-ответу через
127.0.0.42. Для холодного reboot удалён именно кэш списков; подписка сохранена.
После исправлений CLI/UI заново прошла singbox_single_process на обеих ВМ,
включая сохранение PID и nft при втором процессе и stale procd PID.

manual_restart_contract, latency_reload_serialization и ShellCheck нового
конкурентного теста прошли. Существующий shell_inventory не прошёл из-за
трёх уже существующих support/*.sh: тест разрешает только full-uninstall.sh.
Это отдельное устаревшее ограничение теста; оно не изменялось ради PASS.

Стендовые VLESS/HTTP серверы на соседней ВМ используются только при остановленном
Forkop той ВМ, чтобы её исходный watchdog не остановил тестовый relay как второй
sing-box. На проверяемой ВМ работает единственный procd-managed runtime.
Подписка локальной фикстуры переводит только один тестовый HTTPS URL в HTTP;
настоящие Discord HTTPS загрузки сохраняют проверку сертификатов.

При удалении APK для чистой установки пакетный менеджер удалил неиспользуемые
зависимости. Они заново установлены из репозитория; список пакетов совпал с
исходным после нормализации только трёх версий Forkop.

Предоставленные пользователем настоящий VLESS TCP Reality/Vision и настоящая
HTTPS-подписка отдельно прошли на обеих ВМ: новый холодный запуск, Discord через
выбранную секцию, единственный procd runtime, DNS. Данные доступа в отчёт и
репозиторий не включены. Проверка настоящих звонков Discord не выполнялась.

Опубликованная 1.16.0 воспроизвела ошибку клиента на обеих ВМ. Обновление
1.16.0 → окончательные APK/IPK 1.16.1 прошло на обеих ВМ с настоящей подпиской.
Первый перекрывшийся прогон OpenWrt 24 не засчитывается; отдельный повтор прошёл.
После последней правки сохранения remote ruleset-кэша пакеты пересобраны,
холодный запуск и обновление повторены на обеих ВМ. SHA-256 всех файлов этого
кэша совпал до и после предварительной генерации и проверки конфигурации.

После исправлений блокировки и UI обе ВМ заново проверены на окончательных
APK/IPK: удалены все три пакета Forkop, выполнена чистая установка, добавлена
настоящая подписка, очищены кэши, скачаны Discord-списки через выбранную секцию
и подтверждены полная политика и непустой DNS-ответ. Затем снова установлен
опубликованный 1.16.0, воспроизведена ошибка отсутствующих Discord subnet rules
и выполнено настоящее обновление до окончательного кандидата. PASS на обеих
ВМ: final-installation.log и additional-result.log.
На APK загрузка удалённых зависимостей потребовала временно задать dnsmasq
прямой сервер 1.1.1.1: VMware DNS возвращал FakeIP для downloads.openwrt.org.
Это изменение стенда восстановлено вместе с исходной конфигурацией dhcp.

Обе ВМ восстановлены на три исходных пакета 1.14.9 и исходные конфигурации.
Полные списки пакетов совпали с повторно снятым начальным состоянием; Forkop,
единственный procd sing-box и DNS проверены. Временные relay/firewall правила
удалены, исходные firewall и cron восстановлены. Файлы с предоставленными
данными доступа удалены со стендов. Логи восстановления: restore-final.log.

После дополнительных испытаний обе ВМ ещё раз восстановлены из тех же
исходных файлов и пакетов. Логи: restore-additional.log. Новые резервные копии
не создавались. Подтверждены исходная 1.14.9, точное совпадение списка пакетов,
единственный procd-managed sing-box, работающий Forkop и DNS; автозапуск включён
как до испытаний. Настоящие Discord звонки и физический роутер не проверялись.

## Локализация сообщений перезапуска

По дополнительному запросу добавлены русский и английский тексты причины
отказа занятого ручного restart, общей ошибки restart и другого активного
действия. Занятый manual restart возвращает отдельный статус 75; UI job
передаёт конкретную причину вместо общего Service restart failed. Интерфейс
переводит только известные сообщения, сохраняя прочие диагностические тексты.
Системные журналы остаются на английском.

Четыре frontend-теста, включая русский и английский варианты, и TypeScript
прошли; LuCI bundle и APK/IPK пересобраны. На обеих восстановленных ВМ отдельно
проверены новые lifecycle/UI модули в тестовом каталоге: занятая блокировка,
статус 75, конкретное сообщение и неизменный единственный managed PID.
Системные пакеты и службы ВМ не заменялись. Логи: localization.log.
Полная предыдущая матрица относится к пакетам из full-matrix-SHA256SUMS;
пересборка локализации проверена описанными адресными тестами, без повторения
всей установки и reboot матрицы. Текущие хэши: packages/SHA256SUMS.

shutdown_correctly. Проверены полная стабильная политика, watchdog.ready,
единственный procd-managed sing-box, sing-box check, DNS и оба текста локализации.
