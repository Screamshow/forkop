# Повторное использование проверки SRS — 8 октября 2026

Изменение реализовано и установлено на 192.168.90.1 в локальный backend Forkop 2.0.0. DNS reload пока остаётся исследовательским кандидатом и в эту сборку не включён. X 1.0.1-r1 и отдельный Zapret не менялись. Релиз не публиковался.

## Поведение

Раньше каждый новый временный файл скачанного SRS проверялся запуском sing-box rule-set match, даже когда содержимое совпадало с проверенным активным кэшем. После копирования на flash проверка могла повториться ещё раз.

Маркер .validated теперь содержит stat signature и SHA-256 проверенного содержимого. Для использования маркера повторно проверяются и metadata, и текущий SHA-256. Если кандидат побайтно совпадает по SHA-256 с доверенным файлом, доказательство проверки переносится на кандидат без повторного запуска парсера. Перед переносом повторно проверяются источник и signature кандидата. Публикация всё ещё выполняется через существующие atomic rename, manifests и правила persistent/runtime capacity. Для бинарных SRS итоговое сравнение содержимого также переведено с MD5 на SHA-256; source JSON сохранил прежний путь.

Новый/изменённый SRS разбирается обычным parser. Перед parsing вычисляется digest, после успешного parsing проверяются исходная stat signature и digest: изменившийся во время проверки файл не получает marker. Legacy-маркер без digest один раз проходит parser и обновляется. При недоступном SHA-256 корректность не ослабляется: кандидат отклоняется, старый рабочий кэш остаётся. sha256sum уже доступен в BusyBox обеих ВМ и роутера; новой пакетной зависимости нет.

## Проверки

- Локально ruleset_digest_reuse, ruleset_cache, manual_restart_contract и sing_box_runtime пройдены.
- Новый тест проверяет parser counter: совпавшие байты не разбираются повторно; изменённые байты с тем же размером, повреждённый кандидат, missing/legacy/stale marker, неверный digest и удалённый источник не используют старое доказательство.
- На OpenWrt 24 и 25 пройдены реальные large/nested/malformed/truncated/unsupported/changed SRS, полный cache publication и сохранение последней рабочей версии при ошибке загрузки.
- Реальные проверки также подтвердили RAM-only хранение изменённого SRS при недостатке flash и последующий перенос на flash при восстановлении capacity.
- Обе ВМ прошли полный restart с новым модулем. После тестов production-модуль восстановлен побайтно в прежнюю версию.
- После настоящего reboot обеих ВМ кандидат смог materialize-config cache-only и refresh неизменившегося постоянного SRS без вызова parser. Установленный кандидат на время reboot был активен. Проверены sing-box process count=1, watchdog.ready, forkop-stably-running с реальными table/mark/min_age и localhost DNS. По boot-log от Starting Forkop до финальной latency scheduling строки около 15 с (25) и 13 с (24), но парного baseline нет, ускорение boot по этим цифрам не заявляется.

Технические сбои стенда не были product failures: первые локальные расширенные list_cache/list_cache_space не выполнились из-за отсутствующего jsonfilter и права mount в WSL; эти две проверки локально не считаются пройденными. Реальные проверки runtime/flash publication выполнены на обеих ВМ. Первый подготовительный restart унаследовал изолированный fake curl и пути кэша из fixture-теста: он не смог выполнить служебный запрос и нарушил подготовку fixture. Окружение очищено, обычные restart успешны, fixture создан заново, reboot-проверка повторена. Один дополнительный fixture promotion сначала использовал намеренно повреждённый ранее probe.srs; после повторной компиляции валидного fixture тест прошёл. Статус init.d/forkop после boot отражает завершившийся launcher и может быть not running при полностью здоровом управляемом runtime; использованы фактические проверки core/nft/DNS/watchdog, а не этот launcher status.

## Что означает для cold boot

Гарантированный обнаруженный выигрыш относится к принудительному refresh неизменившихся SRS при manual_restart. Холодный старт со свежим persistent cache и раньше мог не вызывать parser, поэтому одинаковые 4–5 с для каждого reboot обещать нельзя. Когда кэш нужно обновлять, новый путь помогает и после reboot. Runtime-only cache после reboot исчезает, новые/изменённые данные требуют обычной проверки. Первая миграция legacy markers также не даёт полного выигрыша.

Другие ранее установленные оптимизации native readlink и version deadline применяются и к startup. DNS reload способен ускорить cold boot только когда lifecycle действительно применяет/восстанавливает DNS. При уже корректном управляемом DNS startup может пропустить переход. Минимальный возраст core 8 с сохранён.

Следующий отдельный этап — production DNS reload: bounded ожидание нужной конфигурации/instance, поддержка port=0/custom port/multiple instances, fallback и rollback. Временный localhost-query wrapper из предыдущего исследования не переносится в production без этих условий.
